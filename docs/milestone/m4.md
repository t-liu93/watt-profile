## 2. Shared implementation contracts

### C1. Runtime and module boundaries

Keep Python 3.12, one application process/worker, the installation lock and existing collection runtime. Promote HTTPX from development-only to runtime dependencies and regenerate both locks. Use a long-lived `httpx.AsyncClient`, with one upload task owned by FastAPI lifespan; no external worker, broker or extra Pi service. Planned modules are `logger/upload.py` (transport and scheduling), `logger/capacity.py` (synthetic capacity fixture) and `cli/logger_capacity.py` (entrypoint); keep shared contracts independent of both applications.

Separate injectable transport, clock/wait and scheduler seams so network behavior is testable without a live server or sleeping through real backoff. Serial input and sampling keep their existing seams. Execute repository calls off the event loop using short-lived sessions; never hold a transaction or collection lock while waiting for HTTP or backoff. The uploader never acquires serial ownership; collection keeps its independent reader during network waits. Snapshot insertion and upload confirmation remain independent durable transactions.

Start upload only after installation, credentials, migration and runtime initialization. Read the protected upload Token through the existing identity helper; never include it in a URL, status, errors, metrics or logs. Reuse the saved SQLite server origin rather than an environment override. No origin means no outbound request, including on startup, Retry or shutdown. A configured origin enables upload automatically, independently of collection intent and current site. Paused/completed sessions and a collection storage/meter block do not by themselves disable delivery of already committed records.

Shutdown disables scheduling, interrupts waits and cancels/awaits the upload task, closes HTTP resources, then drains collection and disposes the database/installation lock. Finish any already-started database operation before disposal; thread cancellation is not proof that a transaction stopped. A completed valid confirmation may commit atomically during shutdown; otherwise its records remain pending. Ordinary shutdown must fit the existing 30-second Compose grace period. Network deadlines must not delay shutdown by another full request interval.

Preserve the real-mode read timeout of at most one second and bounded joins. Avoid joining an unstarted/current thread or letting a delayed join worker report a fault against a replacement owner.

Temporary preview setup, including thread startup, belongs inside guaranteed cleanup. Release preview bookkeeping and notify waiters on success, timeout, request cancellation, serial error, startup failure and cleanup failure. Finish temporary-preview lifecycle even if release fails, preserving any independently established collection block. Subscribed previews leave collection and its serial owner intact. Preview never creates a session, binds a meter or stores snapshots.

Successful release restores normal controls and permits another preview, configuration, deployment and collection. Genuine close/join failure latches `serial_close_failed` or `serial_join_failed`, preserves unresolved resource ownership, and refuses replacement readers; it must not masquerade as successful release or leave an unexplained `previewing` state. ### C3. Server origin and pending-group selection

Continue accepting only M1 origins: HTTP/HTTPS authority, without userinfo, path, query or fragment. Public connections use HTTPS; owner-managed tunnel HTTP and isolated development HTTP remain supported. Compare origin identity as scheme, normalized host and effective port, without rewriting stored history or credentials.

| Saved origin and change | Behavior |
| --- | --- |
| null → first non-null origin | Allow, even with pending records; wake upload after the settings transaction commits |
| Same effective origin | Allow; no rerouting and no acknowledgement |
| Non-null → different origin or null, pending exists anywhere | Reject with local API 409 `pending_uploads_prevent_server_change`; retain all settings |
| Non-null → different origin or null, no pending | Allow; uploaded history stays local/on the prior server and is not automatically resent |

Recheck pending existence and update settings inside the same SQLite write transaction; enforce this repository-side, not only in JavaScript. An origin-only rejection must not pause collection. Preserve M2 serial-edit pause/drain behavior for serial changes and atomic settings-row updates. Continue expected-session checks. A blocked group counts as pending; there is no escape through clearing the origin, manual uploaded flags or deleting pending records. An unreachable old server must be recovered before changing a non-null origin with backlog.

Extend `select_pending_group(limit, byte_limit, *, excluded_groups=())`; old callers keep their defaults. A group key is the immutable `(device_id, site_id, session_id, source_id, measurement_point_id)` tuple. Select the oldest pending record outside excluded groups, then its homogeneous group, preserving existing reception/record tie-breaking. Return the existing `PendingGroup` with exact stored canonical bytes, descriptors and bounded body. Exclusion changes neither content nor upload state. Keep only one selected batch in flight and no full-backlog in-memory queue. Database/model corruption stops delivery visibly rather than skipping damaged records.

### C4. HTTP request and response handling

POST `origin + /api/v1/ingest/batches` with `Authorization: Bearer …`, JSON content type and the selected `PendingGroup.body`. Keep M1 limits: 200 records, 16,384 canonical UTF-8 bytes per Snapshot, 4,194,304 request-body bytes; no request compression. Use one pooled connection, TLS verification enabled, `trust_env=False`, no automatic transport retries and no redirects. Never retry a credential-bearing redirected request at another origin.

Set connect/pool timeouts to 5 seconds, read/write timeouts to 30 seconds, and wrap the complete network exchange in a 30-second monotonic deadline including response streaming. HTTPX phase timeouts alone are insufficient for the total deadline; see [HTTPX timeouts](https://www.python-httpx.org/advanced/timeouts/) and [async streaming/resource closure](https://www.python-httpx.org/async/).

Request identity response encoding and stream at most 65,536 actual response bytes; reject other content encodings rather than decompress an unbounded response. Read and validate the complete response before acknowledging anything. Only HTTP **200** with JSON media type and a valid M1 confirmation is success. Verify version, device and the exact unique record-ID set, then call the existing `apply_confirmation()` for stored-content revalidation and one atomic local update/checkpoint. A generic 2xx response is not confirmation.

Wrong/missing/extra IDs, duplicate JSON keys, malformed/non-JSON/oversized 200 responses and unsupported response encodings produce fixed `invalid_confirmation` and backoff, with all records pending. Timeout, connection loss and ambiguous response failures also leave the same batch pending. A local confirmation-write failure produces `upload_storage_error`, preserves pending state/checkpoint and retries with backoff; corruption is fatal and uses existing storage-failure coordination. Do not expose response text, credentials or private exception messages.

### C5. Scheduling, retry and isolation

Use monotonic time for schedules and UTC for displayed/persisted timestamps. On startup or first-origin save, attempt immediately if pending exists. Otherwise scan every ten seconds. Confirmed backlog success triggers the next eligible batch immediately, yielding between batches so local API and collection remain responsive. Pause/complete/site switch do not rewrite ownership or remove old-site authorization.

| Outcome | Scheduling and local state |
| --- | --- |
| Valid 200 confirmation | Atomic confirmation; reset transient backoff; immediately select next eligible group |
| 401 | Global `invalid_credential` block until Retry or effective origin change; retain all records |
| 403 / 409 / 422 | Block that group; use matching M1 error code or fixed `upload_http_rejected`; continue other groups |
| 413 | Halve the group's record limit, minimum one, and rebuild from unchanged stored records; a refused one-record batch blocks the group as `batch_too_large` |
| 429 / 5xx / network failure / deadline | Retry the selected batch with 1/2/4/8/16/32/60-second capped backoff |
| Redirect / 404 / 405 | Global `upload_endpoint_error` block; no following Location or automatic endpoint change |
| Other permanent 4xx | Block the group as `upload_http_rejected` |
| Other 2xx or unrecognized HTTP status | `invalid_confirmation` or `upload_protocol_error`; bounded backoff, no acknowledgement |

Trust an application error code only if its strict M1 error response and HTTP status agree. Proxy HTML or malformed error bodies never acknowledge records. For retryable responses, parse Retry-After seconds or HTTP-date, clamp valid delays to 1–60 seconds, and use the ladder if absent/invalid. Keep reduced 413 limits for that group until Retry, origin change or restart, avoiding repeated oversized probes after each success.

Group/global blocks and transient counters are process memory, scoped to the effective origin; clear them on explicit Retry or an allowed effective origin change. Restart reconstructs scheduling from pending rows and may probe again; no record is marked uploaded merely to avoid another rejection. Retry clears blocks/backoff and coalesces a wakeup at the worker's next safe boundary. It cannot start a second request or overlap a database confirmation. A still-invalid credential/group can block again with its actual error. A blocked old group must never starve an authorized newer one.

Restore is disaster recovery, not routine rollback. The disposable Compose regression tests this copy-in and CLI restore form after container recreation. To validate a backup on that disposable project, restore only to a new empty temporary directory:

```sh
WATT_LOGGER_CONTAINER=$(docker compose --env-file deploy/logger/.env.local \
  -p "$WATT_LOGGER_PROJECT" -f deploy/logger/compose.yml ps -q logger)
docker exec "$WATT_LOGGER_CONTAINER" mkdir -m 700 /tmp/watt-profile-backup-copy

  "$WATT_LOGGER_CONTAINER:/tmp/watt-profile-backup-copy/"

  /tmp/watt-profile-backup-copy

  --backup /tmp/watt-profile-backup-copy --data-dir /tmp/watt-profile-restored
```

Compare device/session identity, Token, snapshot canonical bytes and upload flags against the source backup. Never restore over the live volume.

The HTTP, capacity and Compose selectors own their temporary resources; they do not attach to an existing walkthrough or production project. With the locked Python environment active, run from the repository root:

```sh
M4_CHECK_ROOT=$(mktemp -d /tmp/watt-m4-check.XXXXXXXX)
M4_CHECK_PROJECT="watt-m4-check-$(date +%s)-${RANDOM}"
env -u WATT_SERVER_DATABASE_URL -u WATT_SERVER_DATABASE_URL_FILE WATT_TEST_POSTGRES=1 \
  python -m pytest tests/test_m4_pipeline.py -q --basetemp="$M4_CHECK_ROOT/http"
WATT_TEST_M4_COMPOSE=1 WATT_TEST_COMPOSE_PROJECT="$M4_CHECK_PROJECT" \
  WATT_DEV_IMAGE_TAG="$M4_CHECK_PROJECT" WATT_DEV_PORT=18580 WATT_DEV_SERVER_PORT=18581 \
  python -m pytest tests/integration/test_m4_compose.py -q --basetemp="$M4_CHECK_ROOT/compose"
rm -rf -- "$M4_CHECK_ROOT"
```

Use unused loopback ports; the Compose fixture refuses occupied ports, existing project resources (including stopped containers), or existing exact application tags before creating anything. The HTTP driver cuts one successful response after Server commit. The Compose driver freezes its own Server, observes continued sampling and an in-flight request, force-terminates/recreates its own Logger, restores connectivity/grants and checks identities, backlog, CSV and cleanup protection. Its `finally` removes its own project volumes/network/containers and exact app tags, and asserts absence. Base images and unrelated projects remain outside cleanup. A failed driver is failed evidence; resolve the failure before repeating with a fresh project and a new basetemp child.
