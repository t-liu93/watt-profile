# M2: Standalone Logger

> **English — source of truth** · [中文](m2_zh.md)

Status: planned, 2026-10-11. This document specifies M2; no M2 task or acceptance check is claimed complete.

## 1. Goal and how an agent uses this document

Deliver an offline-capable Logger: operator login, site/serial configuration, optional read preview, continuous P1 collection, ten-second snapshots, durable SQLite storage, lifecycle controls, status, restricted cleanup, command-line backup/restore, and containerized browser acceptance. **M2 does not send data to the Centralized Server.** Every normally collected record remains pending. M3 implements the server; M4 implements the Logger uploader and integrated recovery.

Give an agent this document and a task ID. Read the [Agent Guide](../../AGENTS.md), relevant [M1 contracts](m1.md), and current source before implementation. Section 2 fixes shared contracts; section 3 fixes ordered task boundaries and checks; section 4 holds acceptance instructions and evidence. Keep all M2 design, tasks and completion records in this document and its Chinese mirror. The [MVP roadmap](../mvp-roadmap.md) owns milestone scope.

Execute M2-01 through M2-10 in order, accepting each dependency before advancing. Each task includes its own tests. This document does not activate delegation or authorize commits. All new paths, entrypoints and commands below are **planned deliverables**, not claims that they exist. Preserve the accepted M1 parser, canonical Snapshot/upload schema, immutable identities and pure lifecycle transitions. Any necessary shared-contract correction requires matching code/tests and bilingual documentation in the same task; do not silently invent a competing state machine.

Excluded: real uploads or server calls, server registration implementation, local history queries/CSV, token rotation UI, account management, remote management, host networking, other meter profiles, and physical hardware acceptance. Saving a server origin is configuration only. Preview is optional; starting collection never requires a previous successful preview.

## 2. Shared implementation contracts

### C1. Runtime, configuration and module boundaries

Use Python 3.12, FastAPI/Uvicorn, SQLAlchemy 2, Alembic, Jinja2 and existing Pydantic/pyserial. Add runtime dependencies and a production `requirements.lock`; regenerate `requirements-dev.lock` including HTTPX, Playwright and existing checks. Browser binaries are development-only; no Node.js or browser runtime in the Logger image. Package templates, static assets and migrations in the installed distribution, and test installation outside the checkout.

Planned package boundaries under `src/watt_profile/logger/`: `settings.py`/`bootstrap.py` (deployment and installation), `storage/` (schema, migrations, repositories), `sampler.py` (pure windows), `runtime.py` (coordination), `maintenance.py` (storage/backup), `auth.py`/`app.py` (HTTP), `templates/`/`static/` (UI), and `synthetic.py` (development source). Existing `p1`, `contracts` and `serial` modules remain reusable and do not import the web application. Put command entrypoints in `cli/logger.py` and `cli/logger_admin.py`.

`python -m watt_profile.cli.logger` validates settings, holds a nonblocking Linux file lock at `<data-dir>/logger.lock`, upgrades the Logger database, initializes/loads the installation, checks storage, restores intent, and starts one Uvicorn worker. The lock spans migrations through shutdown; a second application or restore/migrate command using the directory fails `instance_busy`. Disable reload and multiple workers. Migration errors or inconsistent installation state fail startup without resetting data. Importing modules creates no files, threads or credentials.

| Deployment setting | Default / contract |
| --- | --- |
| `WATT_LOGGER_DATA_DIR` | `/var/lib/watt-profile`; persistent private directory |
| `WATT_LOGGER_HOST`, `WATT_LOGGER_PORT` | `0.0.0.0`, `8080`; Compose controls host exposure |
| `WATT_LOGGER_INPUT` | `serial`; only `serial` or explicitly selected `synthetic` |
| `WATT_LOGGER_OPERATOR_USER` | Required, 1–64 characters |
| `WATT_LOGGER_OPERATOR_PASSWORD_FILE` | Required readable UTF-8 file; remove one terminal newline, require 16–256 characters; never log its content |
| `WATT_LOGGER_COOKIE_SECURE` | `false` for direct local HTTP; set `true` when serving through HTTPS |

Unknown input modes and invalid deployment values fail startup. Operator credentials are deployment-owned, outside SQLite and snapshots; there are no production default credentials. Provide a setup command using `secrets.token_urlsafe(24)` that writes a new password file with mode 0600 and refuses overwrite. Password changes require application restart. Bind the password file read-only in containers. Ignore local credential/config files in Git.

SQLite owns site metadata, server origin, serial settings and active-session intent; environment variables must not override those saved values on every restart. Expose DSMR 5 serial defaults from M1, with advanced path/baudrate/bytesize/parity/stopbits editing; timeout stays one second in the UI. Preserve M1 validation and decimal serialization. Path is null until configured; synthetic mode needs no serial path. Profile is fixed to `dsmr5_nl`, revision 1. A server origin is nullable and follows M1 C6; no connectivity check is required.

### C2. SQLite and repository interfaces

Implement **all Logger columns, keys, checks and indices in M1 C5**, not PostgreSQL tables. Use the separate Alembic revision `logger_0001`, packaged with the application. Register deterministic grammar/calendar validation functions on every SQLite connection before migration or writes. Validate effective `foreign_keys=ON`, WAL, `synchronous=FULL` and `busy_timeout=5000`. Initial/no-op migrations and malformed direct SQL inserts must be tested; there is no preceding project Logger revision to fabricate.

Use short SQLAlchemy sessions per operation, never share a session across threads. Serialize application mutations through the runtime coordinator; repository transactions enforce correctness independently. Transactions must not span serial reads, a preview wait, or a ten-second drain. Retain M1's exact canonical UTF-8 text, hash, Decimal scale, all nullable fields, flattened projections and ownership validation on insert/load. Snapshot content is immutable. A repeated identical record key is a no-op; different content for that key is a conflict, not replacement.

Required repository operations, with typed inputs/results and transaction ownership in the repository:

| Interface | Contract |
| --- | --- |
| `load_installation()` / `load_lifecycle()` | Revalidate persisted config, active descriptors, intent, fingerprint and both block reasons; never deserialize runtime owners |
| `save_settings(...)` / `save_site(...)` | Validate and update local mutable metadata only; serial changes use C4 coordination |
| `commit_deployment_change(expected_session_id, ...)` | Compare selected session and atomically complete/create/select descriptors and preserve unresolved blocks |
| `bind_meter(...)` / `update_blocks(...)` | Transactional read-modify-write; never overwrite the other block reason |
| `insert_snapshot(snapshot)` | Validate canonical/projection agreement and insert content plus pending state in one transaction |
| `select_pending_group(limit, byte_limit)` | Return oldest homogeneous ownership group plus immutable descriptors and exact stored records; enforce M1 batch limits; no network |
| `apply_confirmation(batch, confirmation, now)` | Fully validate M1 confirmation and stored record content, then update the whole batch and upload checkpoint atomically; already confirmed replay is harmless |
| `get_status()` / `list_sessions()` | Derived aggregates and bounded lists; no persisted duplicate counters |
| `cleanup_completed(session_ids)` | Delete only uploaded rows of completed sessions in one transaction; retain metadata in M2 |

Confirmation support is a storage primitive for M4 and tests, **not a runnable uploader or public acknowledgement endpoint**. Normal M2 execution never calls it. A failed/mismatched confirmation changes no row. Selection and acknowledgement preserve IDs/content across restart.

### C3. Installation identity and local site/session ownership

Data directory mode is 0700; SQLite, WAL/SHM, credential and backup files are private using process umask 0077. Token is `<data-dir>/upload-token`, mode 0600, generated with `secrets.token_urlsafe(32)`. Do not put it in SQLite, logs, exception messages or ordinary status/configuration responses.

Initialization under the installation lock: create and fsync the Token using an atomic temporary-file/rename and parent-directory fsync; then commit the device UUID and initial `logger_config` together. A migration-only database without an installation may reuse a valid already-created Token after interruption. A committed installation with a missing/invalid Token, multiple devices or an inconsistent singleton fails startup `installation_inconsistent`; never regenerate identities or credentials silently. Temporary credential files are private and never treated as completed credentials. A restart or ordinary edit preserves device UUID and Token.

Create a new site with UUID v4 or use an explicitly supplied v4. Address/description default to empty and are limited to 500/2,000 characters respectively. Unknown supplied UUID creates local metadata only; known UUID retains metadata until a separate explicit edit. Do not overwrite known metadata as a side effect of selection. Point ID remains M1's deterministic site UUID5.

Site creation/import alone does not start a session. The operator selects a site and creates a paused session/source; selecting a site while an open session exists requires explicit switch confirmation. Ending a session leaves it completed and selected; another explicit deployment action creates the next paused session, even at the same site. Pause/resume and restart retain the existing session/source. A→B→A creates three sessions/sources and reuses A's point. Switching to the currently selected site while its session is open is rejected as `same_site`; use completion then new deployment to start a new visit.

### C4. Runtime coordination and ten-second sampling

Use one coordinator to serialize lifecycle/configuration commands, one reader thread with exclusive pyserial ownership, and one window coordinator. Bounded shared state holds the latest candidate and latest sanitized preview, not an unbounded telegram queue. No raw frame survives parsing; discard fingerprints from public values. Pass `SerialFactory` and a controllable clock into the runtime for tests. Never execute blocking reads or waits on FastAPI's event loop.

`WindowSampler.offer(reading, monotonic_received)` and `advance(monotonic_now, utc_now)` implement pure half-open windows `[anchor+10n, anchor+10(n+1))`, anchored when collection begins. At an exact boundary, finalize the old window before accepting the new frame. Keep the latest admitted frame by reception order, not meter timestamp. Use the time a complete frame is received; stamp `sampled_at` at actual finalization. Skipped empty windows produce no rows or catch-up copies. Wall-clock jumps never affect elapsed windows. A restart starts a fresh anchor, never reconstructs a candidate from the last persisted row.

The reader/coordinator synchronize reception and boundary processing so a delayed callback cannot put an old-window frame in a new window. Construct the Snapshot once with the active immutable descriptors and one record ID. Do not replace the owner or descriptors while a candidate remains eligible for finalization. Invalid frames/oversize model output are rejected, counted and reported through fixed errors; they cannot crash the loop or persist unsafe data.

| Operation / event | Required behavior |
| --- | --- |
| Start | Require selected open session and configured serial path in serial mode; persist enabled intent before starting. Idempotent for the same active session; no preview prerequisite. |
| Pause | Persist disabled intent, cancel/close the reader immediately, join it, finalize a nonempty tail at its scheduled boundary, then enter idle. Return busy for conflicting transitions. |
| Complete / switch | Disable old intent, drain as above, then commit completion and optional new paused deployment atomically. Until commit, old selection remains authoritative. An interrupted switch leaves the old session selected and paused; do not replay an uncommitted target. |
| Serial settings change | Validate first; pause/drain old owner, then save changed settings. Keep same session/source and require explicit start. Failed save retains old settings and paused state. Metadata/server-only edits do not stop collection. |
| Graceful shutdown | Cancel/join readers and drain at most ten seconds before DB closure. Preserve pre-shutdown enabled intent, unlike an operator pause, so restart can resume. Compose stop grace period is 30 seconds. |
| Disconnect/open failure | Clear framer, expose the appropriate M1 serial error, enter reconnecting while intent remains enabled; retry after 1/2/4/8/16/32/60 seconds, capped at 60. Reset backoff after an admitted frame. Waits are cancellable. |
| No valid reading | After 15 seconds without an admitted frame, expose `no_valid_reading`; continue reading, create gaps, clear this error on a new admitted frame. Do not label mere port ownership as fresh data. |
| Meter change | Observe fingerprint before accepting a candidate; first valid fingerprint binds transactionally. A mismatch blocks, cancels/joins the reader and discards its current uncommitted candidate. Explicit confirmation closes old session and creates a new paused one at the same site; retain storage block. |
| Restart | Recheck storage/write health before honoring persisted intent. Resume only open, enabled, unblocked sessions using M1 `restart`. Never restore preview or pending runtime commands. |

Start cannot overtake stopping, nor may a new owner open until the old thread exits. An unsuccessful close/join remains visibly unavailable and prevents another owner; never pretend a stuck reader was released. Normal stops drain; storage/meter faults discard the uncommitted candidate instead of violating a block. Abrupt death may lose that candidate only; committed rows remain durable.

Preview returns the next admitted reading within 15 seconds. During collecting/reconnecting it subscribes without reopening, resetting or binding a new meter itself; timeout does not stop collection. When idle it uses a temporary exclusive reader and always closes it; no session, fingerprint binding or Snapshot is created. Starting/stopping/another temporary preview and persisted blocked states reject preview as busy/blocked. Disconnect or request cancellation cleans up only the preview subscription/temporary owner. Preview emits sanitized metrics, fields, quality and meter/reception times, never raw bytes or fingerprint.

### C5. Storage pressure, cleanup and backup

Check free space on startup, before snapshot writes and every ten seconds while running. Below 64 MiB, or on a storage write failure, cancel/join the reader, discard candidates, expose `storage_full`, and persist that block when possible. Do not claim the block was saved if the write failed; startup must recheck. Treat database corruption/migration failure as fatal service errors, not a problem solved by deleting readings. SQLITE_BUSY exhausts its configured wait and surfaces a fixed storage error; no tight retry loop or hidden record loss.

Storage resolution requires at least 64 MiB free and a committed/revalidated safe database write (a no-op update of the config inside a transaction), then removes only `storage_full`, disables collection intent and requires explicit start. Neither block-resolution order may remove the other reason. Do not allocate a real full disk for tests; inject free-space/write failures.

Cleanup lists session totals, pending count and eligible uploaded count. Confirmation specifies session IDs; transaction rechecks completed/uploaded conditions. Open sessions and every pending row survive. M2 retains all metadata and performs no VACUUM in the page request. Deletion may create reusable SQLite pages without increasing filesystem free space; report actual space, and never claim cleanup automatically resolved pressure. No automatic eviction, manual uploaded toggle or server deletion.

Provide `python -m watt_profile.cli.logger_admin` subcommands:

- `generate-password --output PATH`: create the C1 password file, refusing an existing destination.
- `migrate --data-dir PATH`: acquire the installation lock and upgrade schema; application startup also migrates.
- `backup --data-dir PATH --output NEW_DIRECTORY`: online SQLite backup API with its own configured connection; never copy only the live main file. Save `logger.sqlite3`, a separate 0600 `upload-token`, and a manifest containing format version 1, device UUID, migration revision and SHA-256 of both files. Directory is 0700 and must not already exist. Include no operator password. Write a completion manifest last; incomplete output is not restorable. Backup may coexist with runtime writes; initialization must already be complete.
- `restore --backup DIRECTORY --data-dir NEW_DIRECTORY`: offline, acquire target lock, require a new/empty target excluding the lock file, verify manifest/digests, Token syntax, database integrity/foreign keys and model/canonical invariants before installation. Stage privately and install only a fully verified set; failure must not expose a partially initialized runnable installation. Refuse overwrite or unknown/newer schema/backup versions. Preserve identities, Token, pending/upload state, intent and blocks. Do not start collection; a later application startup follows normal intent rules.

Backups contain private site metadata and credentials. Protect all files, never print their contents, and never restore over an existing installation. Test backup during WAL activity and restore to a different temporary directory. A backup does not include deployment credentials/settings outside the data directory; restoring requires those to be supplied separately.

### C6. Authentication and local HTTP contract

Use one deployment-owned operator account, a form login and opaque `secrets.token_urlsafe(32)` session IDs. Keep sessions in process memory, cap at 32 (evict oldest), expire eight hours after creation and revoke on logout/restart. Compare credentials using constant-time digests; human credentials must never use the device-Token hash as a substitute. No account DB, password-reset UI or roles. Rate-limit login to ten attempts per remote address per minute using a bounded in-memory map; do not trust forwarded client headers by default.

Cookie: `watt_logger_session`, HttpOnly, SameSite=Lax, path `/`, configured Secure flag, eight-hour max age. Use independent random CSRF tokens bound to pre-login/session state; validate login and all authenticated mutation requests, including registration reveal and preview. Do not enable cross-origin access. Validate same-origin Origin where supplied; render escaped text and never embed untrusted HTML. Missing authentication yields API 401 or redirects page requests to login; missing/invalid CSRF yields 403. Authenticated/private responses use `Cache-Control: no-store`. No body, password, Token, serial bytes or fingerprint in access/application logs or validation errors.

Use `/api/local/v1` for the following JSON endpoints. Pydantic models reject unknown keys; IDs/times/decimals reuse M1 types. Every success returns `{"data": ...}` except 204; every error returns `{"error":{"code":"...","message":"fixed safe text"}}`. Validation is 422 with no echoed inputs, missing objects 404, conflicts/busy/blocks/stale selection 409, unavailable serial/preview timeout 503, storage failure 507. POST commands wait for completion without blocking the event loop (preview ≤15 seconds, ordinary drain ≤10 seconds), then return final state. Client timeout is not proof of rollback; reload status before retrying.

| Method and relative path | Input → output / semantics |
| --- | --- |
| `GET /status` | → `StatusView` below |
| `GET /config` | → saved server origin, serial fields and fixed profile; no credentials |
| `PATCH /config` | Supplied mutable config fields plus required `expected_session_id` (UUID or null) → saved config; compare selection before C4 change |
| `GET /sites` | `offset=0`, `limit=50` (1–100) → `{items,total}` ordered by UUID; items contain UUID/address/description |
| `POST /sites` | `{site_id?: UUID,address?: str,description?: str}` → site; omitted ID generates v4. Existing supplied ID returns stored metadata unchanged. |
| `PATCH /sites/{site_id}` | Address and/or description → updated site; no identity change |
| `POST /deployment` | `{site_id,expected_session_id,confirm_switch: bool}` → `StatusView`; compare selection, require confirmation if current session is open; C3/C4 create or switch |
| `POST /sessions/{session_id}/start`, `/pause`, `/complete` | `{}` → `StatusView`; path must match current selected session; same-state repeat is idempotent where M1 permits |
| `POST /preview` | `{}` → sanitized `ReadingView`; no session prerequisite |
| `POST /meter-change/confirm` | `{expected_session_id}` → new paused deployment status; only with meter-change block |
| `POST /storage/resolve` | `{}` → `StatusView`; health/write checks before removing storage block |
| `POST /registration-summary` | `{site_id}` → `{site_id,address,description,device_id,token}`; explicit authenticated reveal for a known local site |
| `GET /sessions` | Same pagination as sites → `{items,total}` ordered by `started_at,session_id`; descriptor IDs, state, intent, ended_at and total/pending/eligible counts |
| `POST /cleanup` | `{session_ids: [UUID],confirm: true}`, 1–100 unique IDs → `{deleted_count,retained_pending_count,free_bytes}`; reject any unknown ID before deletion; open sessions remain untouched |

`POST /deployment` with stale expected selection fails without mutation. This protects double-click/retry and old tabs from creating extra sessions. Start/pause/complete targeting an old session cannot affect a newer one. The same protection applies to serial configuration and meter confirmation. Metadata-only edits may occur while collection is active.

`ReadingView` consists of `meter_time_raw`, `meter_time_utc`, `received_at`, the 18-key `metrics`, sanitized `fields` and `quality`, using M1 serialization. `StatusView` wraps the unchanged M1 `LoggerStatus` as `logger` plus `input_mode`, `upload_mode="not_implemented"`, `persisted_blocks`, `active_session_state` (open/completed/null), `latest_live_reading` (ReadingView/null), `active_session_latest_received_at` (persisted MAX/null), and `runtime_error` (fixed code/null). M1 latest/pending aggregates cover all stored sessions; the additional active-session timestamp prevents old-site history looking like current collection. Latest live reading is in-memory, cleared on session change/restart; it is not proof of persistence. Errors not in M1's collection enum, such as `snapshot_invalid`/`storage_error`, use `runtime_error` instead of silently extending the wire contract. M2 upload error is null and normal upload-success time is null; display the saved checkpoint if a test/restored database contains one, together with upload mode.

Page routes: `GET /login`, `POST /login`, `POST /logout`, and protected `GET /`. Login form fields are `username,password,csrf_token`; success redirects to `/`, failed login uses a generic message. JSON mutations supply `X-CSRF-Token`, server-rendered forms a hidden token. `GET /health/live` reports event-loop liveness; `GET /health/ready` returns 200 after initialization/migration/runtime setup, 503 during startup/shutdown or fatal DB/runtime failure. Unauthenticated health responses contain only a boolean. Missing site, disconnected meter, persistent collection block or absent server does not make an initialized service unready; these are visible product states.

### C7. Browser behavior

Serve one small English dashboard with settings/site, reading preview, collection/status, registration and maintenance sections. Poll status every two seconds without overlapping requests. Refreshing a page must not replay mutations. Disable conflicting controls while starting/stopping/previewing; still enforce all rules server-side. Display a persistent **Synthetic input — development only** banner in synthetic mode and **Upload not implemented in M2; records remain pending** in both modes.

First use: log in → create/import site → create paused deployment → save serial settings (real mode) → optionally preview → start. Server origin may remain empty. Preview before site creation is also available. Show all 18 metrics with units, null as “Unavailable”, UTC and original meter time, sanitized fields and quality issues. Distinguish live preview, latest saved current-session time and all-session backlog; do not expose fingerprints.

Pause and resume reuse the session. Complete, site switch, meter replacement and cleanup require confirmation describing consequences and current IDs. Known-site selection preserves metadata; editing it is a separate action. Registration explicitly reveals then copies UUID/address/description/device/Token, clears revealed content on leaving the section/logout, and does not put Token in localStorage or a URL. Provide selectable text if clipboard API is unavailable on local HTTP.

Maintenance lists sessions/counts with pagination and eligible cleanup selections; explain why pending/open-session rows are protected and why normal M2 data cannot yet be cleaned. Storage resolution is an explicit check, followed by a separate start action. Login expiry, busy conflicts, stale selection, serial errors and storage failures are visible with reload/retry guidance, not silent successes. No charts, local historical-reading table, CSV or backup-download UI.

### C8. Synthetic input and containers

Synthetic mode implements the same `SerialFactory`/read/close seam and emits bounded chunks of valid DSMR 5 telegrams once per second, with synthetic identifiers, advancing timestamps/counters and correct CRC. Feed bytes through the real framer/parser/profile/runtime; do not inject ready-made snapshots. Keep the synthetic meter fingerprint stable across recreation. Tests can inject bad CRC, silence, disconnect/reconnect and replacement through fixtures/fakes; expose no production fault-injection HTTP endpoint.

Deliver `deploy/logger/Dockerfile`, `deploy/logger/compose.yml`, a tracked configuration example with no real credentials, and root `docker-compose.dev.yml` with service `logger`. Build a Python 3.12 slim image supporting local architecture and Linux ARM64. Runtime is non-root with a documented fixed UID/GID 10001; a narrowly scoped volume-initialization service prepares only the mounted data volume for that UID and exits, with no serial device. Application never runs privileged. Real serial deployment uses explicit device mapping to `/dev/p1` and configured supplementary device GID; no blanket `/dev` mapping. Document password-file readability by the application UID without making it world-readable.

Development: synthetic source, `127.0.0.1:8080:8080`, disposable project-scoped data volume, no host serial device, no server/PostgreSQL and no external volumes. A development-only setup service creates the documented synthetic account `operator` / `watt-profile-dev-only` password file in a private project volume. Never reuse this setup/default in standalone deployment. Root Compose must remain extensible for M3 services. Standalone Compose uses serial mode, requires the password file and device/GID variables, and preserves its data volume on normal down/recreate. Configure healthchecks against readiness and `stop_grace_period: 30s`.
