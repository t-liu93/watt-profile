### C2. P1 framing, privacy and admission

#### Protocol basis

The sole profile is `dsmr5_nl`, revision `1`, based on the [Netbeheer Nederland DSMR 5.0.2 specification](https://www.netbeheernederland.nl/sites/default/files/2024-02/dsmr_5.0.2_p1_companion_standard.pdf), especially §§6.1–6.4, 6.12–6.13 and 7.1. Its serial defaults are 115200 baud, 8 data bits, no parity, one stop bit. CRC covers the original bytes from `/` through `!`, inclusive; preserve CRLF. DSMR version field `1-3:0.2.8` must equal `50`. The OBIS group F suffix shown in specification tables is not part of the wire code.

The implementation is application-read-only: no serial data writes or GPIO/request-line management. Use a compatible USB/P1 cable that handles the physical interface and activation. Other DSMR versions and unverifiable telegrams are rejected by this profile, even though the parser can report their integrity.

#### Parser interfaces

- `TelegramFramer(max_frame_bytes=16384).feed(chunk: bytes) -> list[bytes]` incrementally returns complete frames; `reset()` discards a partial frame. Expose only a numeric discarded-frame counter for diagnostics.
- `parse_telegram(frame: bytes) -> P1Telegram` reports `valid`, `invalid`, or `unverifiable`; malformed structure raises `P1ParseError` with a fixed safe reason code (`malformed_frame`, `non_ascii`, `frame_too_large`).
- `map_telegram(telegram, received_at) -> MappedReading | None` applies profile admission and maps metrics. `None` means rejected, with a separately exposed safe rejection code (`invalid_crc`, `unverifiable_crc`, `unsupported_profile_version`, `no_electricity_metrics`). `MappedReading` is a standard-library dataclass; M1-04 adds conversion to shared types without making the mapper import Pydantic.

Use the source project's parser/data classes as a starting point, not its permissive stream behavior. Framing requires a `/` start, a line-start `!` footer, four hexadecimal CRC characters, and CRLF termination. A complete malformed footer may reach the parser for an `unverifiable` diagnostic, but cannot pass profile admission. Ignore leading noise; an unexpected new line-start `/` replaces an unfinished frame. On overflow discard that frame and seek the next start. Consume large chunks incrementally so the retained buffer never exceeds 16 KiB, including header/footer. Do not join old half-frames after reconnect.

CRC verification precedes decoding or redaction. Reject non-ASCII bodies and malformed OBIS lines rather than silently losing their meaning. Preserve field order and duplicate occurrences; malformed numeric values are mapping issues, not raw-text exceptions. The parser does not retain frame bytes after returning sanitized objects. CRC diagnostics and errors never contain raw telegram content.

#### Persistence-safe fields

`SanitizedField` contains `code: str`, `raw_values: list[str]`, `value: Decimal | null`, `unit: str | null`, and `redacted: bool`. Decimal values serialize as strings. Preserve duplicate occurrences in a list, not a code-keyed dictionary.

The safe-value list is closed: version, P1 timestamp, tariff indicator, the metrics in C3, standard power-failure counters/event log (`0-0:96.7.21`, `0-0:96.7.9`, `1-0:99.97.0`), phase sag/swell counters (`1-0:32/52/72.32.0` and `.36.0`), and M-Bus type/readings (`0-n:24.1.0`, `0-n:24.2.1`, n=1–4). Store only values matching the profile's declared numeric, timestamp, unit and event-log grammar. Preserve multi-parenthesis group structure; do not interpret every event-log group as a scalar.

Equipment identifiers, message text `0-0:96.13.0`, any other free text and unknown OBIS values become `raw_values=["<redacted>"]`, `value=null`, `unit=null`, `redacted=true`. An unsafe value in an otherwise safe code is also redacted and marked with a field issue. Never trust a value merely because it is numeric or because the code contains `96`. Unknown codes are retained without their values; unknown lines that are not valid OBIS syntax are rejected.

The parser may compute SHA-256 equipment fingerprints for local equality checks, with `repr=False`; all wire/persistence serializers exclude these internal comparison fields. Only the local source binding may retain the main meter fingerprint. M-Bus fingerprints are not stored. Manufacturer header text is not persisted or printed. Fixtures use synthetic IDs, then calculate CRC over the final bytes; no production captures, Tokens or addresses.

#### Admission and quality

Accept only structurally parsed, CRC-valid version-50 telegrams with at least one valid common electricity metric. Never admit invalid/unverifiable frames. Missing, malformed, negative, wrong-unit or duplicate common metric fields produce `null` for that metric, without inventing zeros or selecting a duplicate arbitrarily. Other valid metrics remain usable. No cross-phase or M-Bus substitution.

Quality is `integrity="valid"`, `frame_length: int` (1–16384), `issues: list[FieldIssue]`. Each issue has `code: str | null` and one reason from `missing`, `invalid_value`, `invalid_unit`, `duplicate`, `redacted`, `invalid_timestamp`, `clock_offset_mismatch`. Deduplicate identical issues and order by code then reason. Missing L2/L3 alone is not an error; absent optional diagnostics are not errors. Required-by-profile version failure rejects the telegram. Issue messages never echo received values. Before emitting a mapped reading, normalize malformed/negative/wrong-unit safe fields to redacted values with null numeric/unit data, carrying their original safe issue codes into quality. Missing issues cover the six total/cumulative metrics and L1 metrics; L2/L3 absence is normal. Sort null codes before non-null codes.

### C3. Electrical and time mapping

All names describe the customer's grid connection: import is delivered to the customer, export is returned to the grid. All metric values are nonnegative `Decimal | null`. Standard zeros are real values, not absence.

| Metric | Wire OBIS | Unit |
| --- | --- | --- |
| `energy_import_t1_kwh` | `1-0:1.8.1` | kWh |
| `energy_import_t2_kwh` | `1-0:1.8.2` | kWh |
| `energy_export_t1_kwh` | `1-0:2.8.1` | kWh |
| `energy_export_t2_kwh` | `1-0:2.8.2` | kWh |
| `power_import_kw` | `1-0:1.7.0` | kW |
| `power_export_kw` | `1-0:2.7.0` | kW |
| `voltage_l1_v`, `voltage_l2_v`, `voltage_l3_v` | `1-0:32.7.0`, `1-0:52.7.0`, `1-0:72.7.0` | V |
| `current_l1_a`, `current_l2_a`, `current_l3_a` | `1-0:31.7.0`, `1-0:51.7.0`, `1-0:71.7.0` | A |
| `power_import_l1_kw`, `power_import_l2_kw`, `power_import_l3_kw` | `1-0:21.7.0`, `1-0:41.7.0`, `1-0:61.7.0` | kW |
| `power_export_l1_kw`, `power_export_l2_kw`, `power_export_l3_kw` | `1-0:22.7.0`, `1-0:42.7.0`, `1-0:62.7.0` | kW |

Do not use the legacy misleading `phase_power_current` names. Do not persist derived cumulative totals; future analysis can sum both tariffs only when both are present. Preserve supplied precision, validate unit spelling, and never use binary float arithmetic. Single-phase fixtures omit L2/L3; three-phase fixtures use distinct phase values to expose cross-wiring.

`meter_time_raw` is the sanitized `0-0:1.0.0` string or null. Only the lexical form `YYMMDDhhmmss[S|W]` may be retained; unsafe strings are redacted in fields and become null here. Map years to 2000–2099. `S` means UTC+02:00 and `W` means UTC+01:00; convert to `meter_time_utc` with a timezone-aware UTC result. A missing timestamp produces a `missing` issue. An impossible calendar date produces null UTC with `invalid_timestamp`. Check the suffix against `Europe/Amsterdam` for that instant; retain the suffix-based UTC with `clock_offset_mismatch` if inconsistent. Never infer a suffix, resolve using the Pi's local timezone, or substitute reception time.

`received_at` is UTC wall-clock time when the complete frame is extracted. If one read contains several frames, preserve processing order even if timestamps tie. `sampled_at` is the UTC time of window finalization, not the meter time. Later queries default to `received_at`; meter time remains separately inspectable. No artificial monotonic relationship is imposed on meter timestamps or cumulative counters; decreases remain observable for later analysis.

### C4. Domain and lifecycle types

#### Identity and immutable descriptions

| Identity | Creation and lifetime |
| --- | --- |
| `site_id` | UUID v4 created offline for a new site; existing-site flow accepts a supplied v4, never matches by address |
| `device_id` | UUID v4 generated once per Logger installation and retained across Token changes |
| `session_id` | UUID v4 per monitoring deployment; pause and restart preserve it |
| `measurement_point_id` | `uuid.uuid5(site_id, "grid-connection")`; one grid point per site in MVP |
| `source_id` | UUID v4 per session, kind `p1_serial`, profile `dsmr5_nl`, profile revision 1 |
| `record_id` | UUID v4 generated once when a snapshot is created; never regenerated on retry |

`SessionDescriptor` contains `session_id`, `device_id`, `site_id`, `started_at` (UTC). `SourceDescriptor` contains `source_id`, `session_id`, `measurement_point_id`, `kind`, `profile_id`, `profile_revision`. These descriptors are immutable, repeated on upload, and never contain address, Token, serial path or fingerprint. Every snapshot carries all six IDs; validators check consistency with both descriptors. The point ID must match the site-derived value.

`Snapshot` contains the six IDs, `schema_version=1`, `meter_time_raw`, `meter_time_utc`, `received_at`, `sampled_at`, `metrics` (all 18 C3 metric keys, absent values explicitly null), `fields` (sanitized list), and `quality`. No raw frame or credentials. The 18 keys comprise four cumulative, two total-power, and twelve phase metrics.

Pydantic shared models reject unknown keys and naive datetimes. Parse UTC offsets and normalize to UTC; serialize ISO 8601 using `Z` and six fractional-second digits. JSON metrics/field decimals accept only null or nonnegative finite plain decimal strings; no numbers, exponent notation, Infinity or NaN. Internal construction accepts `Decimal`, never floats. Include all declared nullable keys on serialization. Validate the scalar fields as well as field privacy, known units and size limits; do not merely trust a client's `redacted` flag. Enforce safe-field grammars again at the transport boundary.

#### Local configuration, state and status

Keep address/description and server URL in local configuration, outside snapshots. Serial configuration contains path and profile defaults; allow explicit parameter overrides for diagnostics, without claiming other profiles are supported. A change to path/serial parameters pauses the old owner and clears its framer, but does not relabel history. Profile/source bindings are immutable; a later profile change needs a new session.

Generate the upload Token once with `secrets.token_urlsafe(32)`, store it as a separate 0600 file in a 0700 data directory, and expose it only through the authenticated registration-summary operation. Server registration stores its SHA-256 digest, verifies without logging the Token, and supports disablement. This hash policy is for high-entropy device Tokens, not human passwords. Local and administrator authentication implementations belong to M2/M3.

Persist session state `open|completed` and operator intent `collection_enabled: bool`. An open paused session can resume; a completed session cannot. Explicit completion or switching site closes the old session and creates a new session/source before collection. A new session at an existing site retains its point ID. A first accepted main-meter fingerprint binds the source locally; a later different fingerprint stops collection with `meter_changed`, and requires explicit confirmation and a new session. Missing fingerprint cannot establish or replace identity; mark a missing identifier issue without inventing one.

Runtime collection states are `idle|previewing|starting|collecting|reconnecting|stopping|blocked`. Stable error codes include `serial_busy`, `serial_unavailable`, `serial_permission`, `no_valid_reading`, `meter_changed`, `storage_full`. Preview alone never creates snapshots or a session. Restart resumes enabled, uncompleted sessions only; storage or meter-change blocks persist until resolved. Local lifecycle state stores unresolved reasons independently in `persisted_blocks` (a tuple of unique `meter_changed|storage_full` codes). Setting or resolving one reason must preserve the other across restart. Storage resolution pauses collection and requires explicit start; meter-change confirmation creates a new session/source while retaining any unresolved storage block. These local state fields do not change the upload wire contract.

`LoggerStatus` includes collection state, current IDs (nullable), latest accepted `received_at`, latest collection error code, last successful upload UTC, last upload error code, pending count, pending bytes, oldest pending reception time, free bytes and storage-blocked flag. `DeviceStatus` distinguishes `last_authenticated_contact_at` and `latest_reading_received_at`. Healthy transport with old backlog must not be labeled fresh collection.

### C5. Storage and migration contract

#### Scope and column notation

This is the M1-05 design specification, not executed DDL, a migration, or a repository implementation. M2 implements the SQLite Logger and M3 the PostgreSQL Server. Shared columns below exist in both databases unless marked Logger-only or Server-only. Local state, configuration, fingerprint and storage helpers never extend the C6 wire models.

Every row below defines one column unless explicitly listing the 18 individually named metric rows. `NN` means `NOT NULL`; `NULL` means nullable. `—` means **no SQL default**: the writer must supply the value, including explicit null for nullable Snapshot fields. Defaults shown are SQL defaults, not identity generation. IDs and descriptor times are supplied by the accepted domain constructors; no database-generated replacement identities. All FK updates/deletes use `NO ACTION` (no cascades); application metadata removal must first prove it has no references.

| Type shorthand | SQLite definition | PostgreSQL definition | Constraint / representation |
| --- | --- | --- | --- |
| `U4`, `U5` | `TEXT` | `UUID` | Canonical lowercase UUID text in SQLite, version 4 or 5 and RFC variant as named; native UUID with the same version/variant check on Server. Validate SQLite full `8-4-4-4-12` hex grammar, hyphens and version/variant positions, not length alone. |
| `UTC` | `TEXT` | `TIMESTAMPTZ` | SQLite full valid UTC calendar/time text `YYYY-MM-DDTHH:MM:SS.ffffffZ`, six fractional digits; reject invalid dates. Server accepts aware timestamps, uses UTC session/output timezone and the C4 serializer. No implicit local-time conversion. |
| `HASH` | `TEXT` | `TEXT` | Exactly 64 lowercase hexadecimal characters (`[0-9a-f]{64}`), not merely a 64-character string. |
| `DEC` | `TEXT` | unconstrained `NUMERIC` | Nullable plain nonnegative finite decimal; SQLite full `[0-9]+(?:\.[0-9]+)?` grammar, PostgreSQL nonnegative and finite (exclude NaN and both infinities). No precision/scale cap, REAL, float or exponent conversion. |
| `JSON` | `TEXT` | `JSONB` | SQLite valid JSON; prescribed root kind and shape below. No raw frame/credentials. PostgreSQL root-kind checks plus application shape validation. |
| `BOOL` | `INTEGER` | `BOOLEAN` | SQLite `CHECK (column IN (0,1))`; PostgreSQL native boolean. |
| `INT` / `TEXT` | `INTEGER` / `TEXT` | `INTEGER` / `TEXT` | Strict integer/text inputs; further checks below. |

For nullable types, checks allow SQL null only where the column is marked `NULL`. Migration constraints implement lexical/type/root-kind checks; the application also revalidates accepted domain models before writing/reading. Full calendar validity, UUID5 site derivation, nested JSON privacy/ordering, decimal lexical scale and canonical-byte/hash agreement require shared model/codec validation; simple SQL type checks cannot establish them. Initial migrations must implement any SQLite calendar/grammar checks with deterministic validated functions or equivalent complete expressions, and arrange those functions on every connection before writes. PostgreSQL finite-NUMERIC checks must suit its supported version. Exact expression implementation and negative tests belong to M2/M3, not a claim of executed checks here.

| `logger_config.timeout` | DEC | NN | `'1'` | CHECK positive and finite; seconds, interruptible runtime uses C7 |
| `logger_config.persisted_blocks` | JSON | NN | `'[]'` | Array with only unique `meter_changed,storage_full`; preserve tuple order; zero, one or both reasons |
| `logger_config.last_successful_upload_at` | UTC | NULL | `NULL` | Logger-only status checkpoint; set in confirmation transaction, survives local cleanup |
| `device_credentials.credential_id` | U4 | NN | — | Server-only PK |
| `device_credentials.device_id` | U4 | NN | — | FK → devices; credential rotation preserves installation |
| `device_credentials.token_sha256` | HASH | NN | — | UNIQUE; high-entropy Token digest only |
| `device_credentials.created_at` | UTC | NN | — | Writer supplies registration time |
| `device_credentials.disabled_at` | UTC | NULL | `NULL` | Disabled credential cannot authenticate |
| `device_site_authorizations.device_id` | U4 | NN | — | Server-only composite PK part; FK → devices |
| `device_site_authorizations.site_id` | U4 | NN | — | Server-only composite PK part; FK → sites |

`logger_config` is Logger-only; the other two tables are Server-only. SQLite CHECKs enforce `persisted_blocks` array shape, permitted string members and uniqueness (maximum two elements); writer revalidates `Lifecycle.persisted_blocks`. It is never a single last-error code. Setting/resolving a reason is a transactional read-modify-write preserving the other reason. Meter confirmation/new deployment removes `meter_changed` and retains unresolved `storage_full`; storage resolution removes only `storage_full`, pauses intent and requires explicit start. Persist changes with session/source/config updates atomically. If storage failure prevents a block-state commit, do not report it durable: startup must recheck free space/write health before honoring enabled intent.

Runtime `collection_state`, `latest_error`, `stop_action`, `next_site_id`, serial owners and preview candidates are not durable columns. Restart rebuilds state from active session, intent, source binding and unresolved blocks via `restart`; an interrupted switch has no new session until its transaction commits. Status is computed: latest reception uses `MAX(received_at)`, upload success uses the persisted `last_successful_upload_at` checkpoint, pending count/oldest reception and canonical UTF-8 byte totals use pending rows; error fields are current runtime observations, free bytes from the volume, storage-blocked from unresolved reasons. Server `latest_reading_received_at` is `MAX(received_at)` and is not `last_authenticated_contact_at`. No status counter duplicates a Snapshot field.

The local Token remains solely in a separate 0600 file within the 0700 data directory, never in SQLite/JSON/logs. Server stores only its digest; disabling credentials/removing a grant does not delete descriptors/readings. Profile defaults are a design default for DSMR5, not hardware acceptance of every meter/cable.

#### Ownership keys, foreign keys and indices

In both databases declare these UNIQUE candidate keys even where the single-ID PK implies uniqueness: points `(measurement_point_id,site_id)` and `(site_id,kind)`; sessions `(session_id,device_id,site_id)`, `(session_id,site_id)` and `(session_id,device_id)`; sources `(source_id,session_id,measurement_point_id)` and `(session_id)` (one source per session in MVP). SQLite composite FKs require matching UNIQUE column order/collation.

In addition to single-column FKs in the tables, sources `(session_id,site_id)` references sessions `(session_id,site_id)` and sources `(measurement_point_id,site_id)` references points `(measurement_point_id,site_id)`. Snapshot `(session_id,device_id,site_id)` references sessions' matching key; `(source_id,session_id,measurement_point_id)` references sources' matching key; `(measurement_point_id,site_id)` references points' matching key. This prevents cross-device/session/site/point rewiring even when each individual ID exists. The derived `sources.site_id` supplies relational enforcement of descriptor bindings without a wire change. Validate deterministic point ID before creating points and on model load. Server ingest separately checks the current device-site authorization; historical sessions do not FK to the removable grant.

#### Sanitized lifecycle and cleanup examples

All labels here are synthetic aliases for generated v4 IDs and site-derived v5 points; no actual address, Token or meter identifier is needed. Installation D at site A creates point PA, session SA and source XA. Pause/restart keeps SA/XA/PA. Switching to site B stops/drains the old owner, completes SA with collection disabled, then atomically creates PB/SB/XB and selects SB paused. Old A snapshots and their canonical descriptors/IDs stay unchanged and may still upload under A's grant. Returning later to A creates SC/XC and reuses PA; no address matching or source/profile relabeling. A failed switch transaction leaves the prior committed deployment selected; recovery cannot claim B was committed.

| Synthetic session | Before manual cleanup | After cleanup |
| --- | --- | --- |
| SA completed | R1 uploaded, R2 pending, R3 uploaded | Delete R1/R3 only; retain R2 and D/A/PA/SA/XA metadata |
| SB open, paused | R4 uploaded, R5 pending | Keep both, including uploaded R4 |
| SC completed | R6 uploaded, no pending | R6 eligible; metadata may be retained, removal only if no snapshots/other FK references/config selection |

Cleanup selection/deletion is one transaction and rechecks completed state plus uploaded status. Pending rows cannot be deleted, even when old, blocked by revoked authorization, or on a full disk. Configuration switches/credential disablement do not cascade. A confirmation lost before local acknowledgement leaves R2 pending; an exact server duplicate confirmation later can mark it uploaded, after which it becomes eligible only because SA is completed. Local cleanup never requests server deletion.

#### Durability, migrations and validation plan

M2 enables SQLite foreign keys on **every connection**, WAL, `synchronous=FULL`, and a 5-second busy timeout. Validate effective pragmas. Create a snapshot, projections, canonical text, hash and pending state in one transaction. Apply a fully validated C6 batch confirmation as one transaction setting all requested rows uploaded with confirmation time; content is immutable. Session completion/site switch/meter binding/block resolution also use transactions across affected state/config rows. M3 validates descriptors/authorization and inserts accepted batch content transactionally, with database PK enforcement and conflict recheck under concurrency; contact tracking follows its independent C6 rule.

Keep every record of open sessions. No automatic local expiry or pressure deletion. At less than 64 MiB free in the data volume, or a storage write failure, stop adding records, expose/persist `storage_full` when possible and release the owner. Exactly 64 MiB does not trigger the numeric threshold but does not guarantee a write succeeds. Prior committed rows keep their pending/uploaded state. Resolution requires adequate free space and a successful safe write check, removes only this block, pauses collection and needs explicit start. The threshold is not a capacity guarantee.

M2 starts its own Alembic/SQLAlchemy SQLite chain at `logger_0001`; M3 starts a separate PostgreSQL chain at `server_0001`, once those dependencies are introduced. Each initial revision creates only its database's tables, typed columns, named constraints/indices and its own revision tracking. Shared definitions do not imply identical DDL. Test fresh setup, repeat/no-op upgrade at head, and upgrade from the preceding **project** revision once it exists; there is no prior project revision for 0001. Do not execute source-project migrations or copy source databases. Later revisions must preserve pending canonical bytes/IDs/hash, intent and both block reasons. No destructive production downgrade is specified.

### C6. Upload schema, confirmation and retry

#### Endpoint and payload

`POST /api/v1/ingest/batches`, `Authorization: Bearer <token>`, `Content-Type: application/json`. Configure a server origin (HTTP or HTTPS, no credentials/query/fragment/path) and append this path. HTTPS verifies certificates; HTTP is for the owner's managed tunnel. No upload depends on VPN provisioning.

`UploadBatch` contains exactly `schema_version=1`, `device_id`, `site_id`, `measurement_point_id`, `session: SessionDescriptor`, `source: SourceDescriptor`, `records: list[Snapshot]`. A batch is nonempty and belongs to one device/site/session/source/point. Duplicate record IDs inside one request are invalid. Session/source descriptors may be created by authorized ingest; devices/sites and their authorization must already exist. Existing descriptors must match; ingest never overwrites site metadata or rewires an existing descriptor.

Limits: 200 records, 16,384 UTF-8 bytes per serialized Snapshot, 4,194,304 bytes per request body. Measure snapshot bytes using the C6 canonical serializer. The body limit applies to received bytes before full JSON parsing; reject compressed bodies in MVP. Exceeding record count or bytes produces `413`; schema errors produce `422`. Bounds include fields and quality, not merely common metrics.

Transport numeric values use the C4 decimal-string policy. Canonical record serialization is the model's complete JSON representation, UTC-normalized and with decimal scale retained, encoded as UTF-8 with sorted object keys, compact separators and no ASCII escaping. Preserve list order; include nulls. Compute `payload_sha256` over these bytes. Different decimal scales/field-list ordering count as different immutable content; the Logger persists and retries the same snapshot representation rather than reconstructing it from current configuration.

#### Transaction and responses

Authenticate the Token and verify the batch device identity, site existence and grant. Update `last_authenticated_contact_at` for valid credentials independently of reading acceptance, including authorized requests that later fail validation; unauthorized site attempts can also count as authenticated contact. An unknown/disabled Token never counts. Body-size rejection at the entry point need not count as contact.

Validate all records and descriptor bindings, then create missing point/session/source metadata and insert readings in one transaction. Exact existing `(device_id, record_id, payload_sha256)` matches are duplicates; an existing ID with a different hash is `409` and rolls back the whole batch. Concurrency must enforce uniqueness and recheck conflicts in the transaction; a blind `ON CONFLICT DO NOTHING` is insufficient. After commit return `200`:

```json
{"schema_version":1,"device_id":"00000000-0000-4000-8000-000000000002","confirmed_record_ids":["00000000-0000-4000-8000-000000000006"]}
```

The confirmation IDs equal the request's ID set and preserve request order, including duplicates already on the server. No partial acknowledgements. The Logger verifies schema version, device and the complete unique ID set before updating any local row. Wrong, missing, additional or malformed confirmation IDs leave the entire batch pending and report `invalid_confirmation`. There is no confirmation based merely on HTTP 2xx.

Errors use `{"schema_version":1,"error":{"code":"site_not_authorized","message":"Device is not authorized for this site.","retryable":false}}`. Messages are fixed safe text without request values, credentials or readings. Reverse-proxy/non-JSON errors must also leave records pending.

| HTTP | Codes | Logger behavior |
| --- | --- | --- |
| 401 | `invalid_credential` | Preserve pending; block upload globally until credentials/configuration change or manual retry |
| 403 | `device_mismatch`, `site_not_authorized` (also unknown site) | Preserve pending; block this ownership group until registration/configuration change or manual retry |
| 409 | `record_conflict`, `descriptor_conflict` | Preserve pending; block group and surface correction needed |
| 413 | `batch_too_large` | Shrink multi-record batches; a single oversized record blocks its group |
| 422 | `invalid_payload`, `unsupported_schema` | Preserve pending; block group and surface correction needed |
| 429 / 5xx | `temporarily_unavailable` when application-generated | Preserve pending; retry with backoff |

#### Uploader behavior for M4

One request in flight, 5-second connect timeout and 30-second total deadline. Normal attempts are every 10 seconds; backlog successes trigger the next batch immediately. Retry delays are 1/2/4/8/16/32/60 seconds, reset after confirmed success; clamp a valid `Retry-After` to 1–60 seconds. Timeout, response loss and ambiguous failure leave the same IDs pending.

Select oldest pending records within an ownership group, bounded by count and bytes. A blocked old group must not prevent an authorized new group from uploading; do not delete or acknowledge skipped records. Do not retry permanent failures in a tight loop. Collection and local commits continue independently while upload is unavailable. Ended local session state and serial configuration are not on the wire; the server does not claim to know session completion in this version.

#### Offline upload examples (M1-06)

From the repository root, use the installed package to validate the synthetic files without sending a request. `request.json` and `replay.json` contain identical immutable records with different JSON formatting; `confirmation.json` confirms the full ID set and `rejection.json` illustrates fixed safe error text. None includes credentials or local configuration.

```python
from pathlib import Path
from watt_profile.contracts.domain import payload_sha256
from watt_profile.contracts.upload import (
    UploadErrorResponse,
    validate_confirmation_body,
    validate_upload_body,
)

examples = Path("examples/ingest")
batch = validate_upload_body((examples / "request.json").read_bytes())
replay = validate_upload_body((examples / "replay.json").read_bytes())
assert [payload_sha256(r) for r in batch.records] == [payload_sha256(r) for r in replay.records]
confirmation = validate_confirmation_body((examples / "confirmation.json").read_bytes(), batch)
rejection = UploadErrorResponse.model_validate_json((examples / "rejection.json").read_bytes())
assert rejection.error.code == "site_not_authorized"
```

`validate_upload_body(body, content_encoding=None)` takes actual received UTF-8 bytes, checks the 4 MiB limit before JSON parsing, rejects compressed bodies and duplicate JSON keys, and raises `UploadValidationError` with a fixed safe `response` and `status_code`. A future endpoint must also bound its input read; this pure validator performs no streaming I/O. Unsupported versions produce `unsupported_schema` (422), count/record/body overflow produces `batch_too_large` (413), and other schema/privacy failures produce `invalid_payload` (422). `validate_confirmation_body(body, batch)` allows reordered IDs but requires the entire unique ID set and matching version/device; failure raises only `InvalidConfirmation("invalid_confirmation")`. It does not acknowledge local rows. `error_response(code)` and `UploadErrorResponse` enforce the declared fixed messages and retryability; `temporarily_unavailable` uses 503 as its default application status (C6 also permits 429/other 5xx).

### C7. Serial ownership, sampling and diagnostic probe

`ReadOnlySerial` exposes only `read(size: int) -> bytes` and `close() -> None`; `SerialFactory` receives an immutable `SerialConfig` (path, baudrate, bytesize, parity, stopbits, timeout=1). `Clock` exposes monotonic seconds, UTC now, and interruptible waits. Production opening on Linux requests pyserial exclusive access; a second owner fails clearly. Within the application serialize owner transitions; do not claim process-local locks protect another application.

M2 owns one background reader and one sampling coordinator in one application process. API operations `start_collection`, `stop_collection`, `complete_session`, `switch_site`, `preview` and `get_status` are domain interfaces, not promised HTTP paths. HTTP/page details are M2 design work. Lifecycle model transitions have pure validation in M1; threads and database integration are M2 work.

Start/stop are idempotent for the same session; conflicting transitions return a busy result. Stop immediately signals cancellation and closes the serial descriptor. Finalize the current nonempty ten-second window once at its scheduled boundary before completing a normal stop/session switch/shutdown, waiting at most 10 seconds; never emit an extra early snapshot. Start cannot overtake `stopping`. Empty windows produce no row. An abrupt process death may lose the uncommitted candidate but cannot erase committed snapshots.

Windows use monotonic elapsed time and contain frames received during that process's half-open ten-second interval. Keep the last admissible new frame by reception order. Do not reuse a prior-window candidate. Assign UTC reception/finalization times from the wall clock; wall-clock jumps do not shorten or lengthen windows. Graceful shutdown releases the descriptor and drains the final window; disconnect clears the framer and reconnects with interruptible backoff. Do not transfer ownership until the old reader has exited.

When collecting, preview subscribes to the current owner for up to 15 seconds without reopening, resetting or interrupting it. When idle, a 15-second temporary preview opens the port and closes it in all outcomes, creating neither session nor snapshot. A preview requested during a transition reports busy. Errors and no-valid-frame timeouts are visible, not fabricated success.

M1 exposes `python -m watt_profile.cli.p1_probe --device <path> --duration 15`, with profile/default serial parameters and optional explicit overrides. It prints sanitized mapped values, counts of frames/admitted/rejected frames and fixed error codes; never raw bytes, header text, fingerprints or identifiers. No `--raw-output` option. Duration must be finite and positive. Exit 0 requires at least one admitted reading and no serial error; exit 1 means serial failure, timeout/no admitted readings or interruption; argparse usage errors return 2. Close on all exits. The CLI is an independent diagnostic tool, not a second reader to run beside the Logger.

M1 tests use fake serial and clocks only. Target-meter/cable trials and prolonged collection on both Pi models belong to isolated later hardware verification.
